# 乗っ取り対策と緊急時の手順

規約上の位置づけ（乗っ取られて踏み台になると利用者の責任）は [05-aws-policy-check.md](05-aws-policy-check.md) を参照。
ここでは「どう防ぐか」「どう気づくか」「気づいたら何をするか」をまとめる。

## 1. どう防ぐか（多層防御）

| 層 | 対策 | 乗っ取られにくさへの効き方 |
|---|---|---|
| 公開するもの | nginx の静的ページと 404 だけ。PHP・DB・アプリなし | 侵入口になる「動くコード」が無い。現実的な侵入経路は nginx 本体の未知の脆弱性くらい |
| 入口 | WAF（3ルールグループ）→ ALB 80 → EC2 は ALB からの 80 のみ。22 は閉鎖 | 総当たりやSSH乗っ取りの経路が無い |
| OS | 起動時に `dnf -y upgrade` で最新パッチ。48時間だけの使い捨て | 既知の脆弱性を残さない |
| 出口 | EC2 の送信は 443 のみ | 乗っ取られても、メール送信(25)・SSH総当たり(22)・他ポートへのスキャンには使えない |
| 認証情報 | IMDSv2 強制、IAM ロールは SSM と CloudWatch Agent だけ | 盗まれても AWS アカウントの操作はほぼできない（ログを書き込む程度） |
| ネットワーク | 隔離 VPC（Peering / TGW / VPN なし） | 他の環境へ横展開できない |
| 期間 | 48時間で honeypot スタックを destroy | 狙われる時間そのものを短くする |

**残るリスク**: nginx の 0day を突かれた場合。確率は低いが、起きると EC2 から 443 宛ての攻撃（他サイトへの攻撃・マイニングプールへの接続など）に使われ得る。これを次の「気づく」「止める」で小さくする。

## 2. どう気づくか

| 仕組み | 何を検知するか | 通知 |
|---|---|---|
| GuardDuty → EventBridge → SNS（base スタック） | 重大度 5 以上の Finding（`Backdoor:EC2/*`, `CryptoCurrency:EC2/*`, `Trojan:EC2/*`, `UnauthorizedAccess:EC2/TorClient` など、EC2 が外へ向けて怪しい通信をしたもの） | **メール**（apply 後に届く確認メールのリンクを押しておくこと） |
| AWS Abuse 通知 | 第三者から「あなたの IP から攻撃が来た」という報告 | ルートの連絡先メール（05 参照。24時間以内に返信） |
| AWS Budgets | 想定外の課金（マイニングで CPU 使用やデータ転送が増えた等） | メール（50% / 80% / 予測100%） |
| 目視（1日数回） | EC2 の CPU 使用率、NetworkOut が急に増えていないか | CloudWatch → EC2 のメトリクス |

通常は Low の `Recon:EC2/PortProbeUnprotectedPort` など「外から届いただけ」の Finding しか出ないので、メールが来ること自体が異常のサインになる。

## 3. 気づいたら何をするか

### 手順1: 隔離（迷ったらまずこれ。5分以内）
**スマホから（外出中）**: GitHub → リポジトリ → Actions → 「緊急隔離（Emergency isolate）」→ Run workflow →
confirm に `ISOLATE` と入力して実行。結果は同じ画面で確認できる。
（GitHub アプリで Run workflow が出ない場合は、スマホのブラウザで github.com を開く）

予備: AWS Console モバイルアプリ（または スマホのブラウザでマネジメントコンソール）→ EC2 → インスタンス → 停止。
SG の差し替えはできないが、停止だけでも通信は止まる。

**PC から**:
```bash
AWS_PROFILE=<管理者> ./scripts/emergency-isolate.sh
```
SG を「ルールなし」の隔離用 SG に差し替え → ALB から外す → 調査用スナップショット → EC2 停止。
これで EC2 からの通信は止まる。外に迷惑をかけ続ける状態をまず終わらせる。

### 手順2: 記録
- [ ] GuardDuty の該当 Finding のスクショと `./scripts/export-guardduty.sh`
- [ ] `./scripts/export-logs.sh` で nginx / WAF ログを退避（侵入の痕跡を探すため）
- [ ] 発生時刻・気づいた経緯・やったことをメモ

### 手順3: 撤収
```bash
# Actions「Terraform」で honeypot / destroy（スマホから承認まで可能）。手元PCなら:
./scripts/tf-init.sh honeypot && terraform -chdir=terraform/honeypot destroy
./scripts/verify.sh teardown
```
- 手順1で作ったスナップショットは Terraform 管理外。調査が終わったら手動で削除（verify.sh の「スナップショット残骸なし」で確認できる）

### 手順4: AWS への連絡（Abuse 通知が来ている場合）
- 通知メールに**件名を変えずに**返信する。内容の例:
  「ご連絡ありがとうございます。対象インスタンスは検証用ハニーポットで、通知を受けて隔離・停止し、関連リソースを削除しました（日時）。今後同様の構成は再開しません。」
- 24時間以内の返信が求められる。返信しないとアカウント停止の可能性がある

### 手順5: 振り返り
- 何が侵入口だったかを nginx / WAF ログと GuardDuty Finding から確認する（スナップショットの中身を調べるのは、隔離した別環境でのみ）
- 記事化するかは別途判断。マルウェアやペイロードそのものは公開しない（05 のルール）

## 4. やってはいけない対応
- 攻撃元 IP にスキャン・アクセスし返す（AUP 違反になり得る）
- 乗っ取られた EC2 を「様子を見るため」に動かし続ける
- 隔離せずに調査から始める（その間も外部へ迷惑がかかる）
